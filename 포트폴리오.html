서비스 개요 & 기획 배경

Biker는 기존 상용 앱(카카오, T맵)이 안전상의 이유로 배달 오토바이에 필수적인 '골목길 숏컷'을 안내하지 못하는 한계를 극복하기 위해 기획된 이륜차 전용 하이브리드 내비게이션입니다.

핵심 문제 해결
  • 상용 데이터 대신 전 세계 자원봉사자가 구축한 오픈스트리트맵(OSM) 기반 BRouter 엔진 채택
  • 백엔드 구축 없이 브라우저 연산만으로 서버 비용 0원 달성 (Serverless)
지원자(조종현) 핵심 역할
  • 하이브리드 아키텍처 설계: 카카오 지도의 시각적 API와 유럽 BRouter의 GeoJSON 라우팅 데이터를 통합.
  • AI 페어 프로그래밍 주도: AI(LLM)에게 명확한 도메인 지식과 로직을 지시하여 단기간에 고도화된 기능 구현.
  • 하드웨어 API 제어: Geolocation API를 통한 초당 위치 추적 및 WakeLock API로 모바일 화면 꺼짐 방지 구현.
  • UX 리스크 최적화: 교통상황 타일(Traffic) 시인성 조절 및 법적 책임 한계 고지(EULA) 적용.

CORE TECH 1 · VECTOR MATHEMATICS
[핵심 기술 1] 벡터 내적(Dot Product)을 활용한 수학적 U턴 감지 레이더 데이터의 한계를 알고리즘으로 극복

오픈스트리트맵(OSM)의 한국 법규 데이터 누락으로 인한 '불법 U턴' 안내 버그를 프론트엔드 연산으로 자체 해결했습니다.

문제 상황 (데이터 결함)

BRouter 엔진은 빠르지만, 한국의 '진입 금지', '불법 U턴' 속성이 오픈스트리트맵에 거의 등록되어 있지 않아 위험한 불법 U턴 경로를 그대로 안내하는 치명적 결함이 발견되었습니다. 데이터베이스를 직접 수정할 수 없는 상황에서 자체적인 스캔 엔진이 필요했습니다.

해결 방안: 벡터 코사인 제2법칙 적용

연속된 3개의 GPS 좌표(A, B, C)를 두 개의 벡터로 치환한 뒤, 벡터의 내적과 아크코사인(Math.acos) 함수를 이용해 각도를 계산했습니다. 꺾이는 각도가 150도 이상일 경우 이를 '비정상적 U턴'으로 규정하고 지도 위에 경고 마커를 렌더링합니다. 

// BRouter가 반환한 경로 배열을 순회하며 U턴 색출
const detectAndMarkUTurns = (pathCoordinates, map) => {
    for (let i = 0; i < pathCoordinates.length - 2; i++) {
        const p1 = pathCoordinates[i];
        const p2 = pathCoordinates[i+1]; // 꼭짓점
        const p3 = pathCoordinates[i+2];

        // 두 벡터 구하기
        const v1 = { x: p1.getLng() - p2.getLng(), y: p1.getLat() - p2.getLat() };
        const v2 = { x: p3.getLng() - p2.getLng(), y: p3.getLat() - p2.getLat() };

        // 벡터 내적 및 아크코사인 각도 도출
        const dot = v1.x * v2.x + v1.y * v2.y;
        const mag1 = Math.sqrt(v1.x*v1.x + v1.y*v1.y);
        const mag2 = Math.sqrt(v2.x*v2.x + v2.y*v2.y);
        let angle = Math.acos(dot / (mag1 * mag2)) * (180 / Math.PI);

        if (angle <= 30) { // 내각 30도 이하 (진행 방향 150도 이상 급격한 회전)
            renderWarningMarker(p2, map);
        }
    }
};

CORE TECH 2 · AUTO-REROUTING & CLIENT COMPUTATION
[핵심 기술 2] 투영 거리 기반 경로 이탈 감지 및 자동 재탐색 클라이언트 연산 고도화 (서버 비용 0원)

실시간 위치(GPS)가 기존 경로에서 이탈했는지를 초당 연산하여, 한계점(40m) 초과 시 백그라운드 재탐색을 수행합니다.

초당 하버사인(Haversine) 연산

사용자가 경로를 벗어났는지 확인하려면 '현재 위치'와 '전체 수만 개의 경로 선분' 사이의 가장 가까운 직교 투영 거리(최단 거리)를 구해야 합니다. 지구의 곡률을 고려한 하버사인 공식을 클라이언트(브라우저) 환경에서 초당 1회씩 직접 연산하여 백엔드 부하를 완벽히 제거했습니다.

거리 기반 상태 관리 (Auto-Rerouting) 알고리즘

단순히 타이머에 의존하지 않고, 정확하게 40m 이상 이탈한 경우에만 useEffect를 통해 자동 재탐색 로직을 Trigger하여 무의미한 API 호출을 방지합니다. 

// React 상태 변화를 감지하는 자동 재탐색 엔진
useEffect(() => {
    if (!currentPosition || !activeRoute) return;
    
    // 전체 경로 선분 중 내 현재 위치와 가장 가까운 선분까지의 거리 연산 (미터 단위)
    const distanceToPath = calculateMinDistanceToPath(currentPosition, activeRoute);
    
    if (distanceToPath > 40 && !isRerouting) {
        setIsRerouting(true);
        // 이탈 감지 됨: 현재 위치를 출발지로 새 경로 API 백그라운드 호출
        handleAutoReroute(currentPosition.lat, currentPosition.lng)
            .finally(() => setIsRerouting(false));
    }
}, [currentPosition]); // 1초 단위로 업데이트되는 GPS 상태에 의존

TROUBLESHOOTING · FUNCTIONAL OPTIMIZATION
[트러블슈팅] 프론트엔드 렌더링 최적화 및 GPS 노이즈 제어 기능 결함 해결 사례

모바일 기기 센서의 한계와 React 렌더링 특성으로 인해 발생한 치명적인 기능적 결함을 프론트엔드 로직으로 해결했습니다.

이슈 1: 방향 센서(Heading) 렌더링 지연

[현상] 스마트폰 방향 센서가 초당 수십 번씩 갱신될 때, React의 useState로 마커 각도를 관리하자 지도 컴포넌트 전체가 재렌더링되며 심각한 프레임 드랍(버벅임)이 발생했습니다.

[해결] Native DOM 직접 제어 (useRef)

React의 가상 DOM 상태 관리를 우회했습니다. 순수 DOM 요소(div)를 useRef에 담아 카카오 마커 객체에 주입한 뒤, 센서 값 변경 시 style.transform = `rotate(${deg})` 속성만 직접 변이(Mutation)시켜 재렌더링 없는 60fps 부드러운 회전을 달성했습니다.

이슈 2: GPS 노이즈로 인한 무한 재탐색(Bouncing) 제어

[현상] 도심 빌딩 숲에서 GPS 신호가 순간적으로 튀는(Noise) 현상 때문에, 실제로는 이탈하지 않았음에도 '40m 이탈' 조건이 충족되어 재탐색 로직이 무한 반복(Infinite Loop) 실행되는 마비 현상이 발생했습니다. 

// [해결] 상태 락(Mutex Lock) 및 쿨타임(Debounce) 메커니즘 적용
const [isRerouting, setIsRerouting] = useState(false);

useEffect(() => {
    // 이탈 조건 만족 시, 현재 재탐색 중(Lock)이 아닐 때만 1회 실행 보장
    if (distance > 40 && !isRerouting) {
        setIsRerouting(true); // Lock On: 후속 GPS 노이즈 무시

        handleAutoReroute(currentPosition.lat, currentPosition.lng)
            .finally(() => {
                // 통신이 완료되어도 3초의 쿨타임 유지 후 Lock 해제
                // (신규 경로와 GPS가 일치하도록 안정화될 시간을 벌어줌)
                setTimeout(() => setIsRerouting(false), 3000);
            });
    }
}, [currentPosition]);

LIMITATIONS & ADVANCEMENT PLAN
[한계 및 고도화 방안] 상용 서비스 대비 부재 기능과 극복 로드맵 Next Step

1인 개인 프로젝트가 가지는 데이터 수급의 태생적 한계점을 명확히 인지하고, 이를 상용 수준으로 고도화하기 위한 방안입니다.

한계 1: 경로 렌더링 및 정적 라우팅

[한계점] 시스템 분리로 인해 경로 선 자체를 실시간 교통상황(초록/빨강) 색상으로 칠할 수 없습니다. 또한 실시간 트래픽 데이터를 배제하고 물리적 최단 거리만 계산하기 때문에, 차가 없는 새벽 시간대에도 뻥 뚫린 대로변을 놔두고 좁은 골목길만 고집하는 약점이 있습니다.

고도화 방향

국가교통정보센터(ITS) 트래픽 데이터와 연동하여, 심야 등 도로가 원활한 시간대에는 알고리즘의 골목길 가중치를 낮추고 대로변 위주로 안내하는 동적 시스템을 설계할 계획입니다.

한계 2: 해외 오픈소스 데이터 오류

[한계점] BRouter가 사용하는 오픈스트리트맵(OSM)은 해외 자원봉사자 데이터베이스입니다. 이로 인해 국내 도로 사정(특히 좁은 골목길의 일방통행, 최근 변경된 진입금지 및 유턴 구역 정보) 업데이트가 상용 앱(T맵 등)보다 느리거나 실제 법규와 조금 다를 수 있습니다.

고도화 방향

사용자가 위험한 역주행 길을 안내받았을 때 즉시 '신고'할 수 있는 기능을 신설하여, 해당 Node를 자체 DB에서 영구 마스킹하는 집단지성 피드백 루프를 구축합니다.

한계 3: 안전 정보 및 음성 안내 부재

[한계점] 주행 시 1초가 급한 배달 라이더에게 필수적인 과속 카메라, 스쿨존, 불법 주정차 단속 구역에 대한 알림 기능이 전무하며, 화면을 보지 않고도 주행할 수 있도록 도와주는 실시간 Turn-by-Turn 음성 안내 기능이 지원되지 않습니다.

고도화 방향

'공공데이터포털'의 단속 카메라/스쿨존 좌표 데이터를 DB화하여 지도에 매핑하고, 브라우저의 Web Speech API (TTS)를 도입하여 300m 앞 좌/우회전 및 과속 경고를 음성으로 송출하도록 고도화합니다.
